# 《Z年纪事：凛冬铁轨》架构评估与下一阶段实施计划

日期：2026-11-11  
适用基线：本地仓库提交 `d53f179`，本轮规划前工作区干净。  
文档性质：实施建议与验收清单；文中的新接口、新文件和里程碑均为待实施内容。

## 1. 结论与阶段目标

项目已经有可运行、可回归验证的游戏主干，下一步应集中于状态交接、模块边界和代表关卡体验。保留现有 Godot 项目与生产管线，采用小步重构，避免一次性重写。

本计划暂以“产出可交给外部玩家测试的版本”为目标。人力、每周投入和发布日期尚未确认，因此使用验收里程碑管理进度，不承诺日历工期。

下一阶段完成时应满足：

1. 战役与夜潜通过明确的输入、输出结构交接，关键结果不会重复入账或遗漏。
2. 夜潜总控不再同时承担全部 HUD、战斗和关卡导演实现。
3. 货场与调车场经过真实路线试玩，目标、绕障、撤离与失败反馈可理解。
4. 普通剧情事件有明确的正式入口，关卡来源和生成方式可追踪。
5. 新环境能够导入、测试和导出游戏，交付包能够独立运行。

## 3. 目标架构与边界

```text
Campaign / CampaignHUD：输入、展示、切场景
             |
CampaignSim：跨夜状态、剧情后果、唯一结算入口
             |
RaidConfig → RaidBridge → NightExplore → RaidResult
                           |
              HUD / 战斗 / 交互 / 关卡导演
                           |
                    玩家、敌人、伙伴节点

SaveGame：跨夜状态的序列化与恢复
关卡规格 → 生成器 → 场景 / manifest → 校验
```

约束：

- 战役状态由 CampaignSim 管理；夜潜不直接修改仓库、天数和永久旗标。
- 夜潜局部状态只存在于当前一局；结算通过一次明确提交进入战役。
- 场景切换由流程层处理；逐步移除 CampaignSim 对 SceneTree 的依赖。
- HUD 展示状态并发出操作意图，不自行执行永久奖励与扣除。
- 保留旧灰盒用于机制验证，停止向旧路径重复新增正式玩法；退出旧路径前先核对测试和工具依赖。
- 普通规则使用直接调用，跨对象通知按需要使用信号；不要为所有函数增加事件总线。
- 不以文件行数作为重构成功标准，以职责是否独立、状态是否只有一个写入方判断。

## 4. M1：固定夜潜输入、输出与结算契约

**优先级最高。先做这一阶段，再大规模拆总控。**

### 4.1 改动范围

计划新增：

- `godot_project/scripts/raid/RaidConfig.gd`：一次出发所需配置。
- `godot_project/scripts/raid/RaidResult.gd`：一次夜潜的最终结果。
- `godot_project/tests/raid_contract_smoke.gd`：交接与重复结算保护。

计划修改：`CampaignSim.gd`、`Campaign.gd`、`RaidBridge.gd`、`NightExplore.gd`，必要时调整对应测试。文件名是建议，实施时可按现有命名习惯微调。

### 4.2 实施步骤

1. 先列出当前 cfg 和 `_return_to_campaign()` 中所有字段，逐一标明类型、单位、默认值、生产方、消费方；尤其核对武器 ID/Dictionary 和背包 Array/Dictionary 的转换。
2. 增加类型化 RefCounted 数据对象。先提供旧 Dictionary 的转换函数，保留现有行为，再逐个迁移调用方。
3. 给每次出发分配局内唯一标识 `raid_id`，配置和结果携带同一标识；战役只接受当前未结算的一局结果。
4. 将夜潜直接回写 `sim.raid` 的逻辑收束为构建 RaidResult；将结算规则集中到战役唯一入口。
5. 旧 RaidSim 临时通过适配函数生成相同结果，避免同时重写旧模拟器。确认节点化路径不再依赖其字段后，再停止为该路径创建完整 RaidSim。
6. 将 bridge.begin 和场景切换逐步移到流程层。切换失败时要有可见错误与明确恢复路径，避免扣除携带物后留在失效状态。

### 4.3 数据契约建议

| 对象 | 建议字段 | 注意事项 |
|---|---|---|
| RaidConfig | raid_id、loc_id、day、seed、load、weapon_id、mate_id、pack_max、cold、night_seconds、sound_on | 时间明确为秒；武器内部数据由 ID 查询；兼容旧接口时显式转换 |
| RaidResult | raid_id、loc_id、reason、带回物品、剩余弹药、hp、warmth、良知与卌变化、救援与击杀计数、搜刮统计、事件记录 | 不携带场景节点引用；不直接写入永久状态 |
| 战役结算 | 当前局标识、已结算状态、last_report | 拒绝重复结果、错误局标识和非法结束原因 |

这不是穷尽字段列表。实施前必须以现有读写清单补齐，尤其区分“已并入 pack 的携带物”和“单独归还的未消耗携带物”，避免双倍返还。

不要借重构修改天亮损失、死亡损失和奖励数值。当前天亮结算按背包索引隔项保留，应先锁定现有行为；是否改成随机损失另开玩法任务。当前夜潜结算进入 report，次日推进另有入口，也应分别验证。

### 4.4 验收

- [ ] 出发扣除一次携带物，结果提交后物资只入账一次。
- [ ] 撤离、倒下、天亮、放弃四种路径均保持既有规则。
- [ ] 同一个结果提交两次，第二次不改变仓库、良知、卌、地点余量和日期。
- [ ] 弹匣余弹、备弹、消耗品及新获得武器不丢失、不重复。
- [ ] report 存档与回基地后的状态一致，日期不会多推进一次。
- [ ] 实际走完“战役出发 → 切夜潜 → 返回结算 → 次日”，不能只调用纯逻辑函数替代全部集成验证。
- [ ] 现有全部测试及新增契约测试通过。

**未来影响：** 新增战利品、武器和伙伴效果时，接入点明确；旧灰盒与正式夜潜可以独立演进。迁移期间最大的风险是字段遗漏和重复应用，因此本阶段不同时调平衡。

## 5. M1 配套：存档替换失败恢复

当前 `SaveGame.save()` 写临时文件后先删除旧档再重命名。临时文件降低了半截 JSON 风险，但删除与重命名之间仍有失去主档的窗口。

建议范围：`autoload/SaveGame.gd`、`tests/save_pause_smoke.gd`。

1. 将临时内容重新解析并校验必要字段后，才进入替换步骤。
2. 保留上一份可读备份，检查每一步文件操作的返回值；失败时恢复或保留旧档，不能默默当作保存成功。
3. 加载时明确主档、备份与残留临时文件的优先级；先验证再恢复，不直接选择最新文件。
4. 增加替换失败、主档损坏但备份有效、残留临时档等测试；继续使用隔离测试路径。
5. 当前版本号不认识即拒绝加载。仅在确实改变存档结构时增加迁移，不要为重构内部对象无故升级磁盘格式。

验收：模拟失败后至少保留一份可读旧档；玩家看到真实保存结果；既有存档可以继续加载。平台文件替换语义需实测，不把多步重命名宣称为绝对原子操作。

**未来影响：** 降低异常退出或磁盘操作失败导致进度丢失的风险，为后续正式测试保留可靠恢复手段。

## 6. M2：按职责拆分夜潜总控

每次只抽一个模块，保持公开行为不变。建议顺序：

| 顺序 | 建议新模块 | 迁出范围 | 保留在总控中的职责 |
|---|---|---|---|
| 1 | NightHUD.gd | HUD 创建、文本和仪表刷新、按钮意图 | 提供可展示状态、处理玩家意图 |
| 2 | NightCombat.gd | 武器选择、攻击节奏、装填、命中与伤害请求 | 组织角色与战斗模块，接收局内结果 |
| 3 | NightInteraction.gd | 搜刮、交互目标选择、长按进度、交互请求 | 执行明确的局内状态变更 |
| 4 | NightDirector.gd | 地标、节拍、机关触发与环境事件调度 | 加载关卡数据、启动和结束一局 |

注意：这些模块名称是建议。温度、噪声、后处理可在上述边界稳定后再决定是否独立，不必一次抽完。

执行要求：

1. 先确定模块输入、输出和持有的状态，避免将大量方法搬到新文件后继续通过 `ctl` 任意访问全部内部变量。
2. 优先用少量明确方法替代跨模块字段写入；HUD 不取得可任意修改的 CampaignSim。
3. 每次迁移后运行受影响套件；阶段结束运行全量回归，并在带画面的场景中检查暂停、层级、输入和生命周期。
4. 保留薄适配入口可以降低迁移风险，但写清移除条件，避免永久维护两套实现。

验收：HUD 可独立隐藏/重建而不改变结算；战斗测试不依赖完整 HUD；退出场景后信号和节点不残留；总控主要负责装配与流程。

**未来影响：** 界面改版、武器扩展、关卡机制调整的改动范围缩小。主要风险是初始化顺序、信号重复连接和释放顺序，需要场景级验证。

## 7. M3：两张代表关卡的体验闭环

### 7.1 选择范围

- 货场：检验潜行、搜刮、半人抉择、伙伴辨识、温度和撤离这一整套基础循环。
- 调车场：检验环境节拍和机关是否真正改变路线与决策。
- 其余地图维持可运行，先登记独特机制、母版来源和待完善项，不同时进行全面翻修。

### 7.2 绕障实施指导

1. 在两张代表地图标记起点、搜刮点、障碍两侧、撤离点，先复现最明显的绕障失败。
2. 检查场景碰撞、生成布局与逻辑米坐标是否一致。寻路网格必须处理 y 轴压缩，不能把屏幕像素当等距世界坐标。
3. 优先评估基于现有生成布局建立共享 AStarGrid2D；若动态障碍和场景需求更适合导航区域，再选择 NavigationAgent2D。选定一种作为正式方案。
4. 静态地图共享可行走信息，角色保存自己的路径；错开重算时间，只有目标移动或路径失效时重算。
5. 明确目标不可达时的行为：调查附近可达点、放弃或恢复巡逻，避免无限撞墙。
6. 环境移动物体的碰撞、视线和导航阻挡分别核验，不假定有视觉效果就有完整阻挡行为。

验收场景：围栏两侧经豁口追踪、箱体旁绕行、伙伴通过窄口、目标不可达、机关改变道路后的行为。先覆盖这些真实失败，再扩测试数量。

### 7.3 试玩与记录

安排至少 3 名未参与开发的玩家各完成一次代表流程；这是建议的第一轮样本，不是统计充分性保证。不给口头路线提示，记录：

| 指标 | 记录方式 | 优先处理信号 |
|---|---|---|
| 目标理解 | 玩家第一次说出目标的时点 | 长时间不知道去哪里或拿什么 |
| 路线与交互 | 卡住位置、按键、现场截图 | 提示与可交互范围不一致 |
| 敌人行为 | 障碍、追踪路径、死亡原因 | 持续撞墙、看不懂的发现或伤害 |
| 抉择反馈 | 玩家选择理由、结算后的理解 | 无法识别代价或后果 |
| 性能 | 测试设备、分辨率、帧耗时 | 敌人集中或节拍触发时明显卡顿 |

先修阻止流程完成的问题，再修难以理解的反馈，最后调整难度。没有确认目标设备前，不承诺具体帧率指标。

**未来影响：** 后续关卡有可复用的质量标准。地图数量不再替代完成度，新增关卡需要提供独特路线、机制或叙事体验。

## 8. M4：统一内容来源与交付流程

### 8.1 剧情入口

先选一个真实主线事件做迁移样本，覆盖成本、奖励、旗标、结果文本和一次性触发。比较现有 `EventData/EventResolver` 与 `CampaignData.STORY` 的表达能力，再确定正式方案。

若采用资源化事件，必须补齐主战役所需效果及校验；若保留 STORY，则明确 EventDemo 为实验入口。不要直接批量转换全部剧情，也不要假定现有解析器已经覆盖主战役所有语义。

验收：新增一个普通事件只改内容资源和注册配置；非法物品 ID、缺失效果参数、重复事件 ID 在运行前或加载时明确报错；重复触发不再发奖。

### 8.2 关卡与生成资产

建立关卡登记表，记录 loc_id、scene、布局源、母版来源、关键物资、独特机关和验收状态。逐步让生成器和运行时消费统一来源，减少在 Python、CampaignData 和 LevelBeats 中手工同步同一事实。

规定生成场景的编辑方式：默认改生成源后重新生成；确需编辑器手工布置时，将手工内容放入明确的独立场景或覆盖层，并验证重生成不会抹掉它。

验收：无源数据改动时重生成结果稳定；有改动时差异可解释；能追溯每张地图的来源。不要在主工作区直接重生成全部资产来碰运气，先用临时输出或隔离检出验证差异。

### 8.3 测试、导出与文档

- 固定实际使用的引擎版本与 Python 依赖；从生成脚本真实导入项整理依赖清单，不凭空猜包。
- CI 先导入再运行全套测试；强化测试执行器，让导入失败、零套件匹配等情况返回失败。
- 增加目标平台导出配置，另做交付包启动验证；headless 全绿不能替代图形环境验收。
- README 只保留当前入口与操作方法；旧“下一阶段规划”标注为历史记录，并链接本计划。
- 自动测试结果记录基线提交与执行日期，避免永久写死“全部通过”的结论。

**未来影响：** 新成员能复现开发环境，内容扩展减少对记忆和人工同步的依赖，交付质量能够持续检查。
